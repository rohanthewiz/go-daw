## Goal

Add a playable virtual piano to the DAW: an on-screen keyboard in the web UI driving a polyphonic synth source through the existing mixer.

## What was built

### 1. Polyphonic synth source — `audio/source/polysynth.go` (new)

`PolySynth` implements the existing `Source` interface (`Read(l, r []float32) int` + `Name()`), so it drops into any channel via the standard `atomic.Pointer` source swap and inherits the full strip (gain, EQ, comp, reverb, pan, group routing).

Key design points, all honoring the project's realtime contract (audio callback never allocates/locks/logs):

- **Note transport**: lock-free ring of 128 events, each packed into one `uint64` (note bits 0–7, on-flag bit 8, 16-bit velocity bits 16–31). Producer side (HTTP handlers) serialized by a mutex the audio thread never touches; publication is slot-store-then-tail-advance, both atomic. Ring-full drops the event (correct failure mode — a lost keypress beats a stalled control plane).
- **Voice pool**: fixed 16 voices allocated in the constructor. Assignment prefers re-strike of the same pitch, then a free voice, then steals the oldest (monotonic age counter).
- **Piano-like envelope**: no sustain segment — 3 ms linear attack, exponential decay (~8 s at the bottom of the keyboard, halving every two octaves like real strings), faster release (-60 dB in ~150 ms) on note-off. Attack ramps from the voice's *current* env so re-strikes/steals are click-free. Voice parks below -80 dB.
- **Timbre**: four-harmonic additive (1, 0.5, 0.25, 0.12 amplitudes), normalized.
- **Stereo**: per-voice constant-power pan ±0.4 by pitch (low keys left, high keys right).
- `ActiveVoices()` for control-plane status; `LevelDB` is a `dsp.ParamCell`.

### 2. Mixer/scene integration — `mixer/state.go`

- `SetChannelSource`: new `case "synth"` (default level -12 dBFS since 0 doubles as "unset" under `omitempty`; headroom for chords).
- `captureSource`: new `*source.PolySynth` case → `{Type: "synth", LevelDB: ...}`. Notes are performance, not mix, so only level persists. Scene version stays 1 (additive change).

### 3. Control API — `web/handlers.go`, `web/server.go`

- New `POST /api/channel/:id/note` → `noteHandler`, body `{note (0..127), on, velocity (0..1)}`. Returns **409** (not 400) when the channel's source isn't a synth so the client can distinguish a mid-performance source swap from a bad request.
- `sourceParamHandler` refactored from an oscillator-only type assert to a type switch; now also handles `synth.level`.

### 4. UI — `web/ui/piano.go` (new), `page.go`, `channelstrip.go`, `main.styl`, `app.js`

- **`PianoPanel` component** (element-builder, matches existing component pattern): docked below `div.console`. 25 keys (two octaves + top C) rendered server-side — 15 white keys in flex flow, 10 black keys absolutely positioned at percentages computed in Go (blacks = 62% of white width, centered on seams). Keys carry `data-idx` 0–24; the client adds the octave base.
- **Channel selector** in the panel header: preselects the first synth channel; non-synth channels are labeled "(→ synth)" and choosing one installs a synth then reloads (the codebase's structural-change convention).
- **app.js piano block**: note posts deliberately **bypass `debounced()`** — every key event matters and order must hold. Mouse/touch via pointer events with per-pointerId note tracking (glissando on drag; strike height on the key sets velocity). Computer keyboard: `A S D F…` whites, `W E T Y U…` sharps (`KEYMAP` idx 0–16), `Z`/`X` octave shift (base clamped C1–C6), `e.repeat` guarded, typing targets ignored. Held-note maps store the *actual MIDI pitch* at press time so octave shifts mid-hold can't strand a note. Key highlight via `data-on`, consistent with the existing attribute-state idiom.
- **channelstrip.go**: `synth` added to the source dropdown + `.src-synth` sub-row with a level slider (`src` target, `synth.level` param).
- **main.styl**: `.piano*` rules following the existing dark-theme vars; `touch-action none` on the key bed; `.src-synth` added to the hidden-row selector.

### 5. Defaults — `main.go`

Channel 3 starts as a synth named "Piano" so the keyboard is playable on first launch (alongside the existing ch1 osc / ch2 live defaults).

## Notes / future ideas

- Notes ride per-keypress HTTP POSTs (~1–2 ms loopback). For remote play or tighter timing, a WebSocket note channel is the upgrade path (rweb supports WS; nothing in-repo uses it yet).
- Possible follow-ons: sustain pedal (space bar), velocity curve setting, more waveform/timbre presets, MIDI-over-WebMIDI input, multi-client key highlighting via a new SSE event type.
