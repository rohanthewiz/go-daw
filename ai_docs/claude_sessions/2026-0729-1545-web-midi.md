## Goal

Let a USB MIDI keyboard play the DAW's polysynth. Two routes were assessed (browser Web MIDI API vs. native Go via gomidi/rtmididrv); chose **Web MIDI** — zero Go dependencies, no CGo additions, ~an hour of work, and everything downstream of `NoteOn`/`NoteOff` is shared with the on-screen piano. Native gomidi remains the upgrade path for headless/lowest-latency play (assessment preserved below).

## Key insight

The hard part already existed: `PolySynth.NoteOn`/`NoteOff` (`audio/source/polysynth.go`) are thread-safe control-plane entry points behind a lock-free ring. A hardware keyboard is just another producer of the same two calls the on-screen keys make — no synth, mixer, or API changes were needed at all. The entire feature is UI shell + client JS.

## What was built

### 1. UI shell — `web/ui/piano.go`

A `midi-box` span in the piano header: status dot (`#midi-dot`) + empty device `<select>` (`#midi-in`, one "MIDI: none" placeholder option). Device enumeration and permission are browser-only concerns, so the server renders only the skeleton; app.js fills it (and hides it where Web MIDI is unsupported, e.g. Safari).

### 2. Client logic — `web/assets/app.js` (Web MIDI block inside the piano section)

Lives inside the `if (pianoKeys)` block so it reuses the existing `noteOn`/`noteOff`/`pianoCh` — hardware notes therefore inherit: bypass of `debounced()`, `POST /api/channel/:id/note`, routing via the piano's "Ch" selector, and on-screen key lighting (`light()` already range-guards notes outside the visible 25 keys).

Design decisions:
- **Note parsing**: omni listen (MIDI channel nibble ignored — single-synth target). Note-on with velocity 0 is treated as note-off (running-status idiom many keyboards use). Velocity maps `v/127`.
- **Stuck-note safety**: `midiHeld` map (note → true); `midiPanic()` releases everything before any rebind and on device loss, so unplugging mid-chord can't strand ringing notes.
- **Hot-plug**: `access.onstatechange` → full `refreshInputs()` rebuild (simpler and trivially consistent vs. incremental patching). Selection preference: currently-bound device → `localStorage["midi-in"]` → first available (fresh profile "just works").
- **Permission denied**: shell stays visible but inert — red dot, disabled select reading "MIDI blocked" — so the user can see why a plugged-in keyboard is silent.

### 3. Styles — `web/styles/main.styl`

`.midi-box` (inline-flex) and `.midi-dot` following the `.conn-dot` idiom: grey `#555` = no device, green = bound, `#ff8d99` red = access denied (`data-live="err"`).

## Deferred / future ideas

- **Native Go route** (headless, lowest latency): `gitlab.com/gomidi/midi/v2` + `rtmididrv` (CGo → CoreMIDI; malgo already makes the build CGo). New `midiin` package: enumerate/open port, callback calls `NoteOn`/`NoteOff` (already thread-safe), device-select API + rescan button (RtMidi lacks reliable hot-plug notify), persist device in scene/config. ~Half a day.
- **Sustain pedal (CC64)**: needs a new event kind in the synth's packed-`uint64` ring — free bits exist; small additive synth change.
- **Pitch bend / mod wheel**: new event kinds + per-voice pitch multiplier in `Read`.
- **Multi-timbral routing** (MIDI ch N → mixer ch N): trivial once a native listener exists; the JS handler currently ignores the channel nibble.
- **WebSocket note channel**: still the fix for the ~1–2 ms per-note HTTP POST latency if playing over a network.
