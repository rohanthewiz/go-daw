## Goal

"Add an interactive tutorial to go-daw similar to how it is done in
`~/projs/go/sketchit/`" — i.e. sketchit's guided tour (`static/js/ui/tutorial.js`):
a step engine that spotlights real UI, asks the user to perform each action, and
detects completion by listening to the app's own signals.

Note the naming collision this creates: go-daw already has a *piano lesson*
tutorial (`tutorial/lessons.go`, `web/ui/tutorial.go`, the `tut-*` CSS
namespace). This session added a second, different thing — a **tour** of the
mixer itself — so everything new is namespaced `tour-*`.

## What was built

### `web/assets/tour.js` (new, ~765 lines) — the whole feature

Self-contained IIFE: injects its own stylesheet, holds its own copy, and is
loaded by its own `<script>` after `app.js`. Written in the same ES5-flavored
style as `app.js` (`var`, `function`, string concatenation).

Engine: `start/exit/toggle`, `goTo(i)` → render card + ring → install the step's
watcher, `markDone()` → ✓ flash → `scheduleAdvance()` → `next()`. A `busy()`
check (focus in an INPUT/SELECT/TEXTAREA) defers the auto-advance so the card
never yanks the spotlight away mid-edit, bounded by `BUSY_MAX_MS` so an
abandoned edit can't freeze the tour.

**16 steps**, following the signal path: welcome (modal) → transport bar →
give ch 1 a source → fader & meter → mute → 3-band EQ → dynamics & filters →
plugin inserts → bus routing → groups & master → metronome → recording →
scene memory → virtual piano → piano lessons (hand-off to the *other* tutorial)
→ shortcut summary (modal).

### Three deliberate departures from sketchit's version

**1. No app-event bus to hook.** sketchit's tour listens to `app.events`
(`toolchange`, `selectionchange`, doc `change`). `app.js` here is a closed IIFE
with nothing exported, and opening it up was not necessary: the mixer already
paints its entire state into the DOM. Detectors are therefore built from four
primitives over the DOM:

```
clicked(sel)        delegated click, capture phase
fired(type, sel)    delegated event; capture so non-bubbling <details> "toggle" is seen
domIs(pred, attrs)  MutationObserver on body; attributeFilter keeps the ~12 Hz
                    meter `style` churn from waking the predicate
settled(pred)       one deferred check at step entry — the post-reload half
any([...])          first to fire wins
```

Because every input route (mouse, computer keyboard, hardware MIDI) funnels
through the same `noteOn`/`light()` and the same `data-on` flags, a step is
satisfied identically however the user did it — the property sketchit gets from
its event bus, obtained here for free from the rendered state.

**2. Reload survival — the big structural difference.** go-daw reloads the page
on every structural change (source swap, module add, scene save/recall) because
the server is the single source of truth. Those are exactly the most interesting
steps, so an in-memory tour would die on them.

```
step N installs → baseline recorded → user acts → POST → reload
                                                           │
resume at step N ◄── sessionStorage ◄─────────────────────-┘
settled(pred) sees the DOM already differs from baseline → ✓ → step N+1
```

`sessionStorage` (not `localStorage`): a half-finished tour should outlive a
reload, not a closed tab. `baseline(key, read)` snapshots "what did this look
like before the user touched it" once per step key and persists it alongside the
position — so "did they change the source?" still has an answer after the reload
the change itself caused. Steps whose action doesn't reload (fader, mute, EQ,
routing) use live event watchers; the reload-y ones (source, modules, scenes)
combine `settled()` with the persisted baseline.

**3. Namespacing.** All ids/classes are `tour-*` (`#tour-card`, `#tour-ring`,
`.tour-head`, `.tour-title`, `.tour-check`, `.tour-bar`) because the lesson panel
already owns `tut-head`, `tut-title`, `tut-progress`, `tut-msg`, `tut-strip`,
`tut-chip` in `main.styl`. Colors are restated from main.styl's theme constants
to keep the module drop-in.

Placement is simpler than sketchit's zone rules: prefer below the target, else
above, else beside it — plus a one-shot `scrollIntoView` on step entry, which
sketchit didn't need but go-daw does (strips are taller than most windows and
`.channels` scrolls sideways). Repositioning polls at 250 ms; scrolling is *not*
redone on that tick, so it never fights the user's own scrolling.

## Go-side wiring (small)

- `web/server.go` — `//go:embed assets/tour.js` + `GET /assets/tour.js`.
- `web/ui/page.go` — `PageData.TourSeen`, passes it to `TransportBar`, adds the
  `<script src="/assets/tour.js">` after app.js.
- `web/ui/transport.go` — the `? Tour` button, the tour's only server-rendered
  surface. Carries `data-seen="0|1"`; `tour.js` reads it to decide whether to
  open itself unprompted, and flips it by POSTing the setting.
- `web/handlers.go` — `tour.seen` added to `settingValidators`; `pageHandler`
  reads it with default `"0"` (an untouched console is a first run).
- `web/ui/channelstrip.go` — each processing `<details>` now carries
  `data-sect` (`gate`, `filters`, `eq`, `comp`, `reverb`, `modules`): stable
  hooks so reordering sections can't silently re-aim the tour.
- `web/styles/main.styl` — `.tour-btn` (metronome-button chassis, accent blue,
  lit via `data-on` while the tour is open).
- `README.md` — feature bullet, a `## The guided tour` section, layout entry.

Launch points: the button, `?` to toggle, `Esc` to close — both keys honoring
the same "never hijack typing" guard `app.js` uses for the piano keys.

## Verification (live, in Chrome, against a scratch server on :8099)

Drove the whole tour and confirmed: auto-open on a fresh console; all 16 steps;
every watcher firing (fader `input`, mute click, EQ slider, comp toggle,
module-add *through the reload*, routing select, metronome `data-on`, piano key
`data-on`); ring correctly wrapping `.transport` and the fader row; card placed
below/above as room allows; `?` / `Esc` / button toggle; Finish tearing down the
DOM, clearing sessionStorage and resetting the button. Zero console output.

The source step was the one real find: on a console whose ch 1 was *already*
`osc`, the "set it to osc" copy is unsatisfiable, since detection is
"changed from baseline". Copy amended to say so out loud ("Already on osc? Flip
it to none and back — the step watches for the change, not for a particular
source") rather than weakening the detector into ticking itself off for free.

`go build ./...` and `go test ./...` pass. `tour.seen` was reset to `0` after
testing so the first real run still gets the tour.

## Notes for next time

- `web/ui/page.go` and `web/ui/transport.go` were already non-gofmt-clean at
  HEAD; new lines match local alignment rather than reformatting the files.
- Adding a tour step for a *new* reload-inducing feature: give it a `key`,
  read a baseline with `baseline(key, read)` inside the predicate, and pair
  `settled(pred)` with a live event watcher via `any([...])`.
- Anything new the tour should spotlight wants a stable hook (an id or a
  `data-*` name), not a positional selector.
